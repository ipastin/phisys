# M0 Foundation

## Goal / Why

Подготовить воспроизводимую engineering foundation MyPhisys: чистый checkout устанавливается
по lockfile, выполняет meaningful checks и ловит нарушение package boundaries локально и в CI.
Это инфраструктура для следующего milestone **M1 Health Data Pipeline** (database, canonical core,
synthetic dataset, ingestion). Deterministic analytics и `What Changed` входят в **M2 Health Intelligence**.
M0 не реализует clinical calculations или product surfaces.

- Owner: владелец репозитория; executor и reviewer определяются при активации плана.
- Разрешённая текущая работа: подготовка handoff docs и импорт оригинальных packs в отдельной ветке; без изменения `main`.

- Proposed implementation branch: `codex/m0-foundation`, от актуального `origin/main` после docs PR.
  Не создавай отдельный worktree без соответствующего разрешения.

## Scope / Non-goals

Accepted M0 stack: pnpm workspace + Turborepo, TypeScript strict, Vitest, lint/format,
package boundary validation, CI и минимальные base apps/packages для исполняемых проверок.
M0 CI по `11 IMPLEMENTATION` включает lint/typecheck/tests/architecture/build и
dependency/secret checks. Точные tool versions, scripts и checker выбираются в executable plan.
Не создавай пустое дерево будущих подсистем только ради target monorepo map.

Вне M0: mobile/web UI, database/Supabase, auth, Health Connect/HealthKit, LLM/Model Gateway implementation,
PDF parsing, FHIR, MCP/API server, widgets/watch/push, deploy/DNS, реальные health data,
production health schemas, baseline/meaningfulness algorithms и `demo:what-changed`.

## Invariants / Architecture impact

Project `02 ARCHITECTURE`, §9: `health-core` не импортирует model/vendor/UI/infrastructure SDK;
`analytics` не пишет Raw/Canonical data. Для M0 проверь как минимум границу domain → provider/UI/infra.
Дополнительные allowed/forbidden edges определи в плане из полного dependency graph и ADR.
Не создавай новые clinical entities или нормализацию units/time для доказательства работы toolchain.
Fixture data — только искусственные технические test cases. Missing никогда не подменяется zero.
Product runtime agents, privacy fallback и Model Gateway здесь не реализуются и не объявляются verified.

## Milestones / Concrete steps

### M0.0 — Разрешить зависимости плана

В repository root проверь `git status --short --branch`, `git remote -v`, `git ls-tree -r --name-only HEAD`.
Последняя команда применима только после появления commit. Проверь root/scoped AGENTS и актуальный source registry.
Убедись, что original packs доступны в versioned `docs/`, сравни актуальный source index и M0 scope.
Заполни exact Node/pnpm/tool versions и необходимые источники их совместимости, проверь local/CI availability.
Выход: утверждённый scope и executable plan без значимых pending fields.

### M0.1 — Toolchain

Создай root workspace и нужные конфигурации, pin runtime/package manager/dependencies, сгенерируй lockfile.
Используй выбранные package manager и установленные инструменты; не обновляй глобальные tools молча.
Задай strict TypeScript, lint, format checks и scripts из таблицы ниже.
Выход: повторная установка по frozen lockfile не изменяет lockfile; commands имеют реальные implementations.

### M0.2 — Boundaries и meaningful harness

Добавь только package entry points/exports, нужные для подтверждения выбранной границы.
Boundary checker должен учитывать workspace imports, aliases и относительные межпакетные пути.
Проверь выбранные allowed/forbidden edges из Architecture и ADR, включая запрет model/vendor/UI/infra SDK в `health-core`.
Негативные test cases держи в отдельном test corpus, а не в production graph.
Добавь малый test harness для реальной логики checker; никаких `expect(true)` и `passWithNoTests`.
Выход: неверное ребро в controlled self-test вызывает ожидаемый fail; реальные package checks проходят.

### M0.3 — CI и воспроизводимость

Настрой CI на pull_request и push выбранной integration branch, read-only permissions, без secrets/deploy.
Используй те же pinned runtime и commands, что локально; проверь поддержку workflow для fork PR.
Проверь fresh checkout/install; dependency downloads допустимы, доступ к health/provider services не нужен.
Выход: meaningful lint/typecheck/tests/boundaries/build/format, dependency и secret checks проходят на PR commit SHA.
Если workflow ещё не запускался, CI остаётся `not_run`, M0 acceptance не объявляется выполненным.

### M0.4 — Review и handoff

Проверь diff, фактическую поверхность изменения, negative cases, инструкции воспроизведения и отсутствие scope drift.
Заполни Outcomes и Evidence, приложи reviewable PR. Не merge/deploy автоматически.
Следующий milestone — отдельный M1 plan после принятия M0; UI/real data/LLM не запускаются этим планом.

## Recovery / Idempotence

Перед повтором проверь Progress и существующие файлы; не запускай bootstrap generator поверх готового workspace.
При install failure сохрани diagnostics, исправь причину и повтори install без удаления чужих файлов.
Не меняй lockfile ради прохождения frozen install; обновление dependencies — отдельное объяснённое изменение.
Для negative boundary cases используй test corpus или temporary fixture; cleanup не затрагивает чужой diff.
Если checkout грязный, не делай reset/clean/force push. Scope своих изменений отдели и сохрани.
После review rollback делается отдельным revert PR; `main` напрямую не переписывается.
