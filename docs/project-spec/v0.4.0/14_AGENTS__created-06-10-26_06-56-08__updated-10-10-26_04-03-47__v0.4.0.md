# AGENTS.md — MyPhisys Coding Agent Instructions

## 0. Purpose

Этот документ обязателен для Codex/Claude/другого AI coding agent, работающего с MyPhisys repository.

Твоя задача — реализовывать согласованный **MyPhisys — Personal Health Intelligence System** **без erosion архитектурных, privacy и clinical-safety boundaries**.

Не оптимизируй код ценой нарушения invariants.

## 0.1 Product identity invariant

- Canonical product name: **MyPhisys**.
- Do not reintroduce `Phisys` as a separate platform/masterbrand.
- Do not use `Health AI` as the product name; it is only a generic category/technical phrase when context requires it.
- User-facing conversational CTA: **Ask MyPhisys**.
- User-facing category: **Personal Health Intelligence**.
- Brand/copy/UX changes must read `15 BRAND` before implementation.

## 1. Read before work

Перед значимой задачей прочитай:

```text
00 README
02 ARCHITECTURE
13 ADR
релевантный domain spec
11 IMPLEMENTATION
12 EVALS
```

Если task связан с AI/memory/safety, дополнительно обязательны `05`, `07`, `08` и `16 MODEL_STRATEGY`.

## 2. Priority of truth

При конфликте:

```text
explicit invariant in this file
> Accepted ADR
> domain specification
> existing implementation
> convenience / generated suggestion
```

Не сохраняй существующий код только потому, что он существует, если он нарушает spec. Однако перед breaking refactor зафиксируй migration impact.

## 3. Critical invariants — NEVER violate

### INV-001
LLM не пишет Canonical Health Store напрямую.

### INV-002
Connector пишет только Raw/Source layers.

### INV-003
Agent не получает generic SQL, shell, filesystem или arbitrary network tool.

### INV-004
Persistent clinical fact без provenance запрещён.

### INV-005
Derived analytics воспроизводимы из inputs + algorithm/version/parameters.

### INV-006
AI inference не повышается автоматически до clinical fact.

### INV-007
Missing data не трактуется как zero/normal/negative.

### INV-008
Current State — projection over temporal history.

### INV-009
Authorization/tool permission выполняется вне LLM.

### INV-010
Final C2+ clinical prose строится из verified/policy-approved claims.

### INV-011
Personal health context не отправляется внешнему evidence search без de-identification/minimization.

### INV-012
Connector/provider credentials никогда не попадают в model context/logs.

### INV-013
Core health access/analytics работает без LLM provider.

### INV-014
Natural-language write всегда проходит structured preview + explicit confirmation when required.

### INV-015
Treatment start/stop/dose modification не является executable Agent capability.

### INV-016
Application/domain code references model capabilities, never production model names.

### INV-017
Provider fallback cannot weaken privacy, retention or compliance requirements.

### INV-018
Provider-native memory/history is not MyPhisys memory.

### INV-019
Medical documents remain in MyPhisys storage unless explicit provider-storage policy/ADR approves otherwise.

### INV-020
Model selection is based on MyPhisys task-specific evals, not generic model benchmark rankings.

### INV-021
Large context windows never relax minimum-necessary context policy.

### INV-022
Model availability never grants permission to access additional health context.

### INV-023
High-risk clinical actions remain controlled by deterministic policy outside the model.

### INV-024
MyPhisys core remains useful when all model providers are unavailable.

### INV-025
No production model/snapshot upgrade bypasses capability evals and the release gate.

### INV-026
Surface roles are explicit. Do not implement cross-platform feature parity as a default requirement.

### INV-027
Ambient surfaces (widget/watch/push) expose only privacy-filtered glance/notice/capture capabilities and do not become full clinical reasoning surfaces.

### INV-028
Detailed ambient health values require an explicit surface/privacy policy; full in-app data permission is not equivalent to lock-screen/widget disclosure permission.

### INV-029
Insight generation and notification delivery are separate. Meaningful health push cannot be emitted solely because an InsightCandidate exists.

### INV-030
Ambient/external interactions that require detail, provenance or reasoning resolve to a canonical authenticated full-surface route/context.

### INV-031
Email/messenger/third-party assistant channels cannot become authoritative health write/reasoning surfaces without a new approved ADR plus privacy/security review.

## 4. Architecture rules

### Domain independence
`health-core` must not import:

- OpenAI/Anthropic/provider SDK;
- Supabase implementation;
- React/Expo;
- Health Connect/FHIR implementation.

### Connector isolation
`connectors` must not directly:

- write `analytics.*`;
- generate AI inference;
- decide canonical clinical interpretation;
- bypass ingestion pipeline.

### Agent isolation
`agent-runtime` must not:

- execute SQL directly;
- fetch arbitrary URLs;
- access connector credentials;
- mutate health state outside Tool Gateway/domain workflow.

### Model isolation
Skills must call `model-gateway`, never provider SDK directly.

Rules:

- request `classifier_fast`, `extractor_vision`, `reasoning_standard`, `reasoning_high`, etc.; never `gpt-*`, `claude-*` or another provider-specific ID in domain/skill code;
- privacy level is mandatory for every model request;
- model selection runs after Safety/Context authorization;
- P3 cloud routing is deny-by-default;
- provider memory, provider Files stores and provider-native web search with personal context are disabled by default;
- provider fallback must preserve or strengthen privacy guarantees;
- model/snapshot changes require the model eval release gate;
- read `16 MODEL_STRATEGY` before changing providers, routing, prompt caching, model budgets or model IDs.

## 4.1 Surface delivery rules

If a task affects mobile/web/widget/watch/notifications/MCP/API, read `17 SURFACE_STRATEGY` before implementation.

Required questions for a new surface capability:

1. What user job does this surface solve?
2. Is it Full, Ambient or External?
3. What health data categories are actually required?
4. What privacy mode is permitted?
5. Can it write canonical state? If yes, where is structured confirmation performed?
6. What is the canonical deep-link/handoff target?
7. What happens offline/stale/locked?
8. Does the implementation accidentally create feature parity pressure?

Never put complex clinical interpretation in lock-screen/watch/widget copy when the correct behavior is handoff to a trusted detail screen.

## 5. Preferred implementation style

- TypeScript strict;
- explicit schemas with Zod at boundaries;
- PostgreSQL-first domain persistence;
- small pure functions for deterministic analytics;
- composition over framework magic;
- narrow interfaces;
- explicit errors/status types;
- structured outputs;
- idempotent workers;
- append-mostly health history.

Do not introduce heavy abstraction before a demonstrated requirement.

## 6. Do not add by default

Unless task explicitly requires and ADR approves:


## 7. Data rules

### Raw
Immutable source evidence.

### Canonical
Validated normalized health facts.

### Derived
Deterministic calculations only.

### Inferred
AI interpretation/hypothesis only.

Never store one plane in another for convenience.

## 8. Temporal rules

- preserve effective/recorded/ingested distinctions;
- preserve source date precision;
- never invent `day=1` or `00:00` for unknown values;
- medication/status updates use temporal/versioned semantics;
- point-in-time history must remain reconstructable.

## 9. Provenance rules

Any clinical/imported fact must resolve to Source/Provenance. Any document extraction should preserve page/location when possible.

If provenance is unavailable, do **not** silently create a verified clinical fact. Use candidate/review/quarantine as appropriate.

## 10. Analytics rules

Before implementing a new metric:

1. define MetricDefinition;
2. classify measurement/temporal semantics;
3. specify quality requirements;
4. specify baseline/trend policy;
5. add golden cases.

Do not reuse an algorithm across metrics merely because values are numeric.

Personal baseline ≠ lab reference range ≠ clinical target ≠ user goal.

## 11. AI/runtime rules

Default routing priority:

```text
direct deterministic
→ deterministic skill
→ bounded composite planner only if needed
```

Planner must remain bounded. Never implement `while(agentWantsToContinue)` style unbounded loop.

Numeric/time-series calculations belong to analytics tools, not model reasoning.

## 12. Skill Definition of Done

A skill is incomplete without:

- manifest/version;
- typed input/output;
- permissions;
- allowed tools;
- risk level;
- failure policy;
- tests;
- evals;
- documentation.

Prompt-only skill is not accepted.

## 13. Tool rules

Tool must have:

- stable semantic ID;
- version;
- strict schema;
- narrow permission scope;
- mutability classification;
- risk metadata;
- validated output.

Prefer source-independent semantic capability (`get_metric_series`) over vendor operation (`health_connect_read_hr`).

## 14. Write rules

Agent may propose, not arbitrarily commit.

Typical flow:

```text
propose
→ validate
→ preview
→ approval
→ commit
→ audit
```

Approval is bound to concrete parameters and single-use/expiry where sensitive.

## 15. Safety rules

Do not encode critical clinical safety solely in prompt text.

Use Policy Engine / Tool Gateway / structured claim verification.

Do not implement:

- autonomous medication changes;
- unsupported definitive diagnosis;
- causal claim from correlation;
- emergency routing based on one free-form LLM decision;
- broad external health-data sharing without scoped approval.

## 16. Privacy/logging rules

Operational logs/telemetry must not include raw PHI by default.

Do not log:

- full prompts;
- raw documents;
- health values unless explicitly necessary/approved for controlled debugging;
- credentials/tokens.

Audit metadata and operational logs are separate concerns.

## 17. Testing expectations

Every change should include the lowest appropriate layers:

### Domain change
unit tests + migration/contract tests.

### Analytics change
golden deterministic test + missing/outlier/source-transition edge cases.

### Connector change
contract tests incl. update/delete/revocation/idempotency.

### Agent/LLM change
routing/claim/evidence/safety evals.

### Security-sensitive change
authorization/RLS/approval bypass test.

## 18. Synthetic data

Use synthetic fixtures for routine development/evals. Do not add real personal health data to repository, fixtures, snapshots, logs or screenshots.

## 19. Commit format

Conventional Commits required:

```text

refactor(scope): ...
test(scope): ...
docs(scope): ...
chore(scope): ...

```

One architecture-significant change should not be hidden inside unrelated commit.

## 20. Markdown metadata

Any new/updated `.md` document must include:

Filename also includes created/updated/version metadata following repository convention established by this pack.

## 21. ADR workflow

Create/update ADR when changing:

- domain source of truth;
- data plane semantics;
- agent permissions;
- safety/clinical boundary;
- analytics interpretation semantics;
- storage/deployment topology;
- connector/tool abstraction;
- primary UX mental model.

ADR should contain:

```text
Context
Options (2–3 minimum)
Trade-offs
Decision
Consequences
Migration
Evals/Safety impact
```

## 22. Task workflow for AI agent

For each substantial task:

1. identify relevant specs/ADRs;
2. state affected invariants privately/in implementation notes;
3. inspect current code;
4. implement smallest coherent vertical change;
5. add/update tests;
6. run lint/typecheck/tests relevant to change;
7. update docs/ADR if semantics changed;
8. summarize changed files, decisions, known limitations.

Do not add adjacent features unless necessary for task correctness.

## 23. Definition of Done — feature

Feature is done only when:

- domain contract is explicit;
- provenance/temporal semantics correct;
- authorization/safety reviewed;
- missing/error state handled;
- tests pass;
- relevant eval exists;
- telemetry does not leak PHI;
- docs match implementation.

## 24. Current build order

Do not reorder without explicit reason/ADR:

```text

→ Database / Health Core

→ Metric Registry / Quality / Baseline / Trend
```

## 25. Scope guard

Before Personal Beta, do not implement by initiative alone:

- HealthKit;
- SMART/FHIR direct connection;
- MCP;
- direct wearable APIs;
- correlation mining;
- forecasting;
- family profiles;
- provider messaging;
- treatment/diagnostic automation.

If requested, evaluate against Product scope and ADR before coding.
